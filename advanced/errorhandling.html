Error Handling

Real scripts encounter the unexpected — files that don't exist, windows that don't open, or invalid input. Error handling lets you catch problems gracefully and decide what to do instead of crashing.

Advanced

What is an Error?

In AHK v2, errors are thrown objects. When something goes wrong, AHK creates an error object and "throws" it up through your code. If nothing catches it, the script shows an error dialog and stops. With try/catch, you intercept the error and handle it yourself.

🏀 Think of it like a ball

throw throws the ball. try is the room where things might go wrong. catch catches the ball if it was thrown. finally always runs — whether the ball was thrown or not. else runs only if nothing was thrown (no errors).

Basic try / catch

Wrap risky code in a try block. If it throws, execution jumps to the catch block immediately.

; Without error handling — our script will crash if the file is missing
content := FileRead("C:\nonexistent.txt")  ; ❌ throws!

; With error handling — we catch the problem
try
{
    content := FileRead("C:\nonexistent.txt")
    MsgBox("File loaded: " . content)
}
catch Error as err
{
    MsgBox("Something went wrong: " . err.Message)
}

The Error Object

The catch variable (called err above, but you can name it anything) is an object with useful properties:

PropertyWhat it containsExample value
err.MessageA human-readable description of the error"The system cannot find the file"
err.WhatWhat caused the error (function name, etc.)"FileRead"
err.ExtraExtra context about the error"C:\nonexistent.txt"
err.FileScript file where the error occurred"C:\MyScript.ahk"
err.LineLine number in the script42
 
try
{
    FileRead("C:\missing.txt")
}
catch Error as err
{
    MsgBox(
        "Error: "    . err.Message  . "`n" .
        "In: "      . err.What     . "`n" .
        "Detail: "  . err.Extra    . "`n" .
        "At line: " . err.Line
    )
}

try / catch / else

The else block runs only when the try block completes without any error. It's the "happy path" after your risky code:

try
{
    content := FileRead("C:\data.txt")
}
catch Error as err
{
    ; This runs ONLY if FileRead threw an error
    MsgBox("Failed to read file: " . err.Message)
}
else
{
    ; This runs ONLY if no error was thrown
    MsgBox("File contents: " . content)
}

try / catch / finally

The finally block always runs, regardless of whether an error occurred. Use it for cleanup — closing files, showing a "done" tooltip, re-enabling things you disabled:

ToolTip("Working...")   ; show status

try
{
    content := FileRead("C:\report.txt")
    MsgBox("Loaded: " . content)
}
catch Error as err
{
    MsgBox("Error: " . err.Message)
}
finally
{
    ; Runs no matter what — I use this to clear the tooltip
    ToolTip()
    MsgBox("Operation complete (success or fail).")
}
🧹 When to use finally

Great for releasing resources: closing file handles, clearing a status tooltip, re-enabling a hotkey, or resetting a flag. Even if your catch block has a return, the finally block still runs before the function actually returns.

throw — Raise your own errors

You can create and throw your own errors using throw. This is useful for validating inputs or signalling that something in your own code went wrong:

; Throw a built-in Error object
Divide(a, b) {
    if (b == 0)
        throw ValueError("Cannot divide by zero!")
    return a / b
}

try
{
    result := Divide(10, 0)
}
catch ValueError as err
{
    MsgBox("Caught: " . err.Message)  ; "Cannot divide by zero!"
}

Built-in Error Types

AHK v2 has several error sub-types. You can catch a specific type to handle different errors differently:

Error TypeThrown when
ErrorThe base type — catches everything
ValueErrorA value is invalid (e.g. wrong type, out of range)
TypeErrorWrong type passed to a function
OSErrorOperating system / file system failure
MemoryErrorOut of memory
TimeoutErrorAn operation timed out
TargetErrorTarget window/control not found
 
try
{
    WinActivate("ahk_exe doesnotexist.exe")
}
catch TargetError as err
{
    MsgBox("Window not found: " . err.Message)
}
catch OSError as err
{
    MsgBox("OS error: " . err.Message)
}
catch Error as err
{
    ; Catch-all for anything else
    MsgBox("Unexpected error: " . err.Message)
}

Real-World Example — Safe File Processor

#Requires AutoHotkey >= 2.0
#SingleInstance Force

ProcessFile(path) {
    if !FileExist(path)
        throw ValueError("File not found: " . path)

    try
    {
        content := FileRead(path)
        lines   := StrSplit(content, "`n")
        MsgBox("Lines in file: " . lines.Length)
    }
    catch OSError as err
    {
        MsgBox("Couldn't read file — maybe it's locked?`n" . err.Message)
    }
    finally
    {
        ToolTip()  ; always clear any tooltip
    }
}

{

    }

    }
}
✅ Best Practices
  • Always catch the most specific error type first, then fall back to a generic Error catch.
  • Never swallow errors silently — at minimum, log them with FileAppend() so you can debug later.
  • Use finally for cleanup so your UI never gets stuck in a "loading" state.
  • Validate inputs before doing risky operations, then use throw to signal problems early.
